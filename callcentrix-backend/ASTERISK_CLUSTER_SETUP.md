# Настройка кластера Asterisk (несколько серверов, одна БД)

Это одноразовая настройка **на каждом физическом сервере Asterisk**, которую
нужно применить руками — у backend нет доступа к файлам конфигурации
Asterisk. Приложение управляет только строками в Postgres (realtime) и шлёт
AMI-команды `pjsip reload`/`dialplan reload`; сама возможность серверам
находить друг друга и звонить между собой обеспечивается конфигом Asterisk
ниже.

Предполагается, что realtime для `endpoint`/`aor`/`auth`/`identify` (таблицы
`ast_ps_*`) и dialplan (`ast_extensions`) уже настроены и работают на текущем
единственном сервере — так уже устроен этот проект. Ниже — что нужно
**добавить**, чтобы то же самое расширилось на несколько серверов.

## 1. Разделяемые живые регистрации (`ast_ps_contacts`)

Это ключевой шаг. Сейчас Asterisk хранит живые SIP-регистрации (`Contact`)
только у себя в памяти. Чтобы сервер A мог напрямую позвонить пользователю,
зарегистрированному на сервере B, регистрации должны храниться в общей
Postgres-базе — тогда `Dial(PJSIP/username)` на любом боксе увидит актуальный
контакт, где бы пользователь ни был подключён, и отправит INVITE прямо туда.
Существующее правило дайлплана `_X. → Dial(PJSIP/${EXTEN},30,rU)` (создаётся
в `CreateTenantContext`) менять не нужно — оно уже работает правильно.

В `sorcery.conf` (обычно `/etc/asterisk/sorcery.conf`) на **каждом** сервере,
рядом с уже существующими секциями для `endpoint`/`aor`/`auth`/`identify`,
добавить:

```ini
[res_pjsip]
contact=realtime,ps_contacts
```

Таблица `ast_ps_contacts` — стандартная PJSIP realtime-схема Asterisk. Если
её ещё нет в базе, создать:

```sql
CREATE TABLE IF NOT EXISTS ast_ps_contacts (
    id                        VARCHAR(255) PRIMARY KEY,
    uri                       VARCHAR(511),
    expiration_time           BIGINT,
    qualify_frequency         INTEGER,
    outbound_proxy            VARCHAR(255),
    path                      TEXT,
    user_agent                VARCHAR(255),
    qualify_timeout           DECIMAL(5,3),
    reg_server                VARCHAR(255),
    authenticate_qualify      CHAR(1),
    via_addr                  VARCHAR(255),
    via_port                  INTEGER,
    call_id                   VARCHAR(255),
    endpoint                  VARCHAR(255),
    prune_on_boot             CHAR(1),
    qualify_2xx_only          CHAR(1)
);
```

Это единственная таблица из данного списка, в которую пишет сам Asterisk (не
backend) — в неё ничего провижинить из Go не нужно.

## 2. Порядок идентификации входящих запросов

В `pjsip.conf`, секция `[global]`, убедиться, что:

```ini
[global]
endpoint_identifier_order=ip,username,anonymous
```

Это нужно, чтобы входящий INVITE от другого бокса кластера распознавался по
IP через объект `identify`, который backend создаёт автоматически при
добавлении сервера в админке (см. `internal/asterisk/server.go`,
`writeInterServerTrust`) — по одному `identify` на каждую упорядоченную пару
серверов, с общим контекстом `asterisk-cluster-relay`.

## 3. Контекст `asterisk-cluster-relay` в dialplan realtime

Как и для контекстов провайдеров/тенантов, dialplan realtime подключается
через `switch`, а не читается напрямую из файла — это уже должно быть
настроено в `extensions.conf`:

```ini
[asterisk-cluster-relay]
switch => Realtime/@extensions
```

Backend сам пишет строки этого контекста в `ast_extensions` (одно и то же
правило `_X. → Dial(PJSIP/${EXTEN},30,rU)`, что и в тенантских контекстах) —
руками ничего в контекст добавлять не нужно, только объявить сам контекст в
`extensions.conf`, как уже сделано для `[tenant-N]` и контекстов провайдеров.

## 4. Qualify / NAT

Если серверы находятся в разных сетях (не в одном приватном сегменте),
задать `qualify_frequency`, `rtp_symmetric`, `force_rport` так же, как это
уже сделано для агентских эндпоинтов (`internal/asterisk/sip.go`), и
убедиться, что порты RTP/SIP между серверами открыты в фаерволе в обе
стороны — иначе аудио между звонящими на разных боксах не пройдёт даже при
успешном сигналинге.

## 5. Применение

```
asterisk -rx "core reload"
```

(маппинг sorcery не подхватывается одним `pjsip reload`/`dialplan reload` —
нужен полный `core reload` после правки `sorcery.conf`). После этого шага
всё остальное — добавление серверов, пользователей — идёт через обычный флоу
приложения (`pjsip reload`/`dialplan reload` по AMI, которые backend уже
рассылает на все настроенные серверы при любом изменении).

## Проверка после настройки

1. В админке (SuperAdmin → Тенанты → вкладка «Серверы Asterisk») добавить
   два тестовых сервера.
2. Создать двух пользователей — при 2 активных серверах они должны
   автоматически распределиться по разным боксам (см. колонку «Сервер» на
   странице Пользователи).
3. Убедиться, что оба веб-телефона регистрируются (каждый должен подключаться
   к своему серверу — WS-прокси backend выбирает URI автоматически).
4. Позвонить с одного номера на другой — звонок должен пройти через
   `asterisk-cluster-relay` на удалённом боксе и установиться с двусторонним
   звуком.

# Чёрный и белый список звонящих (func_odbc)

Отдельная от кластера, но той же природы разовая настройка **на каждом
сервере Asterisk** — код за неё уже ссылается на этот файл (см. комментарии
к `EnsureBlacklistCheckSubroutine`/`EnsureWhitelistCheckSubroutine` в
`internal/asterisk/kcnumber.go`), поэтому она документируется здесь же.

## Как это устроено

Backend сам пишет в `ast_extensions` две общие Gosub-подпрограммы —
`[blacklist-check]` и `[whitelist-check]` — и на каждом входящем звонке
вызывает нужную через `Gosub(blacklist-check,s,1(${CALLERID(num)},<tenantId>))`
(белый список — только если для конкретного номера включён переключатель
«Принимать звонки только из белого списка» в настройках IVR, т.е.
`ivr_configs.whitelist_enabled`). Каждая подпрограмма читает результат через
ODBC-функцию — `ODBC_BLACKLISTCHECK()` / `ODBC_WHITELISTCHECK()` — которую
объявляет `func_odbc.conf` на стороне Asterisk. Backend не может создать эту
декларацию сам (как и провайдерские/тенантские контексты в `extensions.conf`
выше) — это и есть недостающий ручной шаг.

**Без этого шага обе проверки молча не блокируют вообще никого**:
`GOSUB_RETVAL` остаётся пустым, условие `"${GOSUB_RETVAL}" = "1"` (чёрный
список) или `"${GOSUB_RETVAL}" = "0"` (белый список) не выполняется — и
звонок идёт дальше как обычно. То есть таблицы `blacklist`/`whitelist` и
админка полностью рабочие и хранят данные корректно, но сам PBX никого не
блокирует, пока это не настроено.

## Настройка func_odbc.conf

На каждом сервере Asterisk, в `func_odbc.conf`, добавить (используя тот же
DSN, что уже настроен в `res_odbc.conf` для realtime-подключения к этой же
Postgres-базе):

```ini
[BLACKLISTCHECK]
dsn=<dsn>
readsql=SELECT CASE WHEN COUNT(*) > 0 THEN '1' ELSE '0' END FROM blacklist WHERE tenant_id = ${ARG2} AND active = TRUE AND (expires_at IS NULL OR expires_at > NOW()) AND (regexp_replace(phone,'\D','','g') LIKE '%'||regexp_replace('${SQL_ESC(${ARG1})}','\D','','g') OR regexp_replace('${SQL_ESC(${ARG1})}','\D','','g') LIKE '%'||regexp_replace(phone,'\D','','g'))

[WHITELISTCHECK]
dsn=<dsn>
readsql=SELECT CASE WHEN COUNT(*) > 0 THEN '1' ELSE '0' END FROM whitelist WHERE tenant_id = ${ARG2} AND active = TRUE AND (regexp_replace(phone,'\D','','g') LIKE '%'||regexp_replace('${SQL_ESC(${ARG1})}','\D','','g') OR regexp_replace('${SQL_ESC(${ARG1})}','\D','','g') LIKE '%'||regexp_replace(phone,'\D','','g'))
```

`ARG1` — это `CALLERID(num)` (не доверенный, идёт от звонящего — отсюда
`SQL_ESC()`), `ARG2` — `tenantId` (подставляется самим dialplan'ом, не
звонящим). Условие с `regexp_replace(...,'\D','','g')` в обе стороны — то же
самое сравнение «только цифры, с любой стороны подстрокой», что и в ручной
проверке из веб-интерфейса (см. `normalizePhone` + SQL в
`BlacklistHandler.Check`/`WhitelistHandler.Check`,
`internal/handlers/blacklist.go` и `whitelist.go`) — специально держится в
двух местах идентичным, чтобы кнопка «Проверить номер» в админке и реальный
dialplan всегда были согласованы.

Проверить точный синтаксис `SQL_ESC()`/`func_odbc.conf` под установленную
версию Asterisk и ODBC-драйвер Postgres (`psqlodbc`) — детали экранирования
между версиями отличаются.

После правки:

```
asterisk -rx "module reload func_odbc.so"
```

(или `core reload`, если модуль ещё не был загружен ни разу).

## Как включается сама блокировка (уровень приложения, после того как func_odbc настроен)

- **Чёрный список** — включён всегда, для всех номеров тенанта сразу
  (default-allow: пропускаем всех, кроме тех, кто в списке). Добавить номер
  на странице «Чёрный список» (SuperAdmin/Администратор тенанта) — он
  блокируется сразу, пока стоит `Активен`; можно временно снять флаг или
  задать срок действия (`durationDays`), не удаляя саму запись. Отдельного
  переключателя «включить чёрный список» нет и не нужно — он не выключаем.
- **Белый список** — по умолчанию выключен и не блокирует никого, это
  отдельный, per-номерной режим. Чтобы включить для конкретного номера: (1)
  добавить разрешённые номера на странице «Белый список»; (2) в настройках
  IVR именно этого номера включить переключатель «Принимать звонки только из
  белого списка» и сохранить. Гейт становится активным только для этого
  номера — остальные номера того же тенанта белый список не проверяют, даже
  если в нём есть записи. **Внимание**: если список пуст, а переключатель
  включён, абсолютно все звонки на этот номер блокируются.

## Проверка после настройки

1. Добавить свой тестовый номер в «Чёрный список» (статус «Активен»),
   позвонить с него на любой номер тенанта — звонок должен уйти в контекст
   `blocked` (короткое сообщение `privacy-sorry`), а не на IVR/очередь.
   Отключить/удалить запись — звонок снова должен проходить как обычно.
2. На тестовом номере включить «Принимать звонки только из белого списка» с
   пустым белым списком — позвонить с любого номера, звонок должен
   блокироваться. Добавить этот номер в белый список — звонок должен пройти.
3. Если оба шага не сработали (звонок всегда проходит) — почти наверняка
   `func_odbc.conf` не настроен или не перезагружен: `asterisk -rx "odbc
   show"` / `asterisk -rx "dialplan show blacklist-check"` помогут увидеть,
   вызывается ли подпрограмма и доходит ли она до ODBC, а лог Asterisk на
   уровне `verbose`/`debug` покажет, пустой ли `GOSUB_RETVAL`.
